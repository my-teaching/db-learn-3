# 2. Что такое Data Mart

**Data Mart — предметно ориентированный аналитический слой, подготовленный под конкретную область задач или группу потребителей.**

Примеры предметных областей:

```text
Sales
Marketing
Finance
Logistics
Support
```

В TechStore тема ЛР3 — **Sales Data Mart**, то есть аналитический слой продаж.

Важно:

```text
Data Mart ≠ один VIEW
Data Mart ≠ одна таблица
Data Mart ≠ схема с названием mart
```

Data Mart определяется прежде всего:

- предметной областью;
- бизнес-вопросами;
- показателями;
- измерениями;
- правилами расчёта;
- понятной гранулярностью аналитических наборов.

В этой работе Sales Data Mart реализуется несколькими представлениями.

# 3. Почему витрина логическая

Возможны два принципиальных подхода.

## Логическая витрина

```text
FactSales + Dimensions
        ↓
       VIEW
        ↓
 аналитический SELECT
```

Отдельная копия агрегированных данных не создаётся.

При обращении к VIEW SQL Server формирует результат на основе текущих таблиц DWH.

Преимущества:

- нет дублирования данных;
- нет отдельного ETL витрины;
- нет отдельного расписания refresh;
- изменения DWH отражаются в результате;
- повторяющаяся аналитическая логика хранится централизованно.

## Физическая витрина

```text
DWH
 ↓
ETL / ELT / materialization
 ↓
готовые физические наборы
```

Такой вариант имеет смысл, когда:

- объём данных велик;
- расчёты тяжёлые;
- одинаковая агрегация выполняется постоянно;
- существует требование по времени ответа;
- допустима задержка между DWH и витриной;
- требуется отдельный жизненный цикл аналитического набора.

После ЛР2 в `FactSales` находится всего `53` строки. Отдельное физическое хранение агрегатов в этой работе не решает реальной проблемы.

Поэтому ЛР3 использует **logical Data Mart на обычных VIEW**.

# 4. VIEW как аналитический интерфейс

Обычный `VIEW` можно воспринимать как:

> именованный табличный интерфейс над запросом.

Базовая форма:

```sql
CREATE OR ALTER VIEW schema_name.view_name
AS
SELECT
    ...
FROM ...
JOIN ...
GROUP BY ...;
GO
```

После создания:

```sql
SELECT *
FROM schema_name.view_name;
```

VIEW позволяет:

- не повторять один и тот же большой `JOIN`;
- централизовать формулы;
- дать бизнес-понятные имена;
- скрыть технические детали DWH;
- предоставить стабильный интерфейс для отчётов;
- ограничить набор доступных полей.

Но обычный VIEW:

- не хранит отдельную копию результата;
- не является автоматическим ускорением;
- не гарантирует порядок строк;
- не отменяет стоимость внутреннего запроса.

# 5. Почему используется схема `mart`

SQL Server schema — пространство имён внутри базы.

В проекте уже используются разные логические области:

```text
dbo
→ основные таблицы

stg
→ промежуточные внешние данные

mart
→ предметный аналитический слой
```

Например:

```text
dbo.FactSales
mart.vw_ProductPerformance
```

Разделение по схемам помогает:

- видеть назначение объектов;
- упрощать сопровождение;
- разделять права;
- уменьшать путаницу между базовыми таблицами и пользовательским аналитическим интерфейсом.

Безопасное создание схемы:

```sql
IF SCHEMA_ID(N'mart') IS NULL
    EXEC(N'CREATE SCHEMA mart');
GO
```

Наличие схемы `mart` само по себе не делает объект настоящей витриной.  
Нужен осмысленный аналитический контракт.

# 6. Пять вопросов перед созданием витрины

Перед `CREATE VIEW` полезно пройти цепочку:

```text
1. Кто потребитель?
2. Какие вопросы нужно решать?
3. Какие показатели нужны?
4. Какие измерения нужны?
5. Что означает одна строка результата?
```

Пример:

```text
Вопрос:
какие категории дают больше выручки по месяцам?

Measures:
Revenue
UnitsSold
OrdersCount

Dimensions:
Year
Month
Category

Grain:
одна строка = один месяц + одна категория
```

После этого SQL становится следствием принятой модели, а не случайным набором `JOIN` и `GROUP BY`.

# 7. Measure и Dimension

## Measure

**Measure** — числовой показатель.

В ЛР3 встречаются:

```text
UnitsSold
Revenue
OrdersCount
TotalSpent
AvgOrderValue
```

## Dimension

**Dimension** — разрез, по которому анализируется показатель.

Примеры:

```text
Year
Month
Category
Product
Customer
City
```

Один показатель может анализироваться по разным dimensions:

```text
Revenue по месяцам
Revenue по товарам
Revenue по клиентам
Revenue по городам
```

# 8. Гранулярность аналитического набора

**Grain (гранулярность)** отвечает на вопрос:

> Что означает одна строка результата?

Примеры:

```text
одна строка = один товар
одна строка = один клиент
одна строка = один город
одна строка = один год + месяц + категория
```

Если grain не сформулирован, легко смешать уровни детализации.

Например:

```text
Month
Category
ProductID
Revenue
```

`ProductID` делает набор детальнее, чем `Month + Category`.

Добавление поля в `GROUP BY` способно изменить смысл всего аналитического набора.

---

# 9. Один Data Mart может содержать несколько grains

В ЛР3 создаётся **один Sales Data Mart**, но внутри него несколько VIEW.

```text
Sales Data Mart
│
├── vw_SalesByMonthCategory
│   grain = месяц + категория
│
├── vw_ProductPerformance
│   grain = товар
│
├── vw_CustomerValue
│   grain = клиент
│
└── vw_SalesByCity
    grain = город
```

Разный grain не означает автоматически разные Data Mart.

Граница Data Mart определяется бизнес-доменом и задачей.  
Grain определяет смысл строки конкретного аналитического набора.

---

# 10. Когда разделять аналитические VIEW

Несколько вопросов могут обслуживаться одним VIEW, если:

- относятся к одной предметной задаче;
- используют совместимые dimensions;
- используют совместимые measures;
- один разумный grain позволяет получить необходимые ответы.

Например набор:

```text
Year
Month
Category
Revenue
UnitsSold
```

может позволить посмотреть:

```text
выручку по месяцам;
выручку по категориям;
выручку по месяцам и категориям.
```

Но вопрос:

```text
какие клиенты дали наибольший оборот?
```

естественно приводит к другому grain:

```text
одна строка = один клиент
```

Поэтому появляется отдельный VIEW внутри той же Sales Data Mart.

---

# 11. Grain исходного `FactSales`

Важно отличать grain факта DWH от grain аналитического VIEW.

В проекте:

```text
FactSales
1 строка = 1 товарная позиция заказа
```

Один заказ может содержать несколько товарных позиций.

Например:

```text
Order 1001
├── Laptop
├── Mouse
└── Keyboard
```

Это три строки `FactSales`, но только один заказ.

Отсюда:

```sql
COUNT(*)
```

считает строки факта,

а:

```sql
COUNT(DISTINCT OrderID)
```

считает заказы.

---

# 12. `COUNT(*)` и `COUNT(DISTINCT ...)`

Пусть набор содержит:

```text
OrderID  Product
1001     Laptop
1001     Mouse
1001     Keyboard
1002     Monitor
```

Тогда:

```sql
COUNT(*)
```

вернёт:

```text
4
```

а:

```sql
COUNT(DISTINCT OrderID)
```

вернёт:

```text
2
```

Показатель `OrdersCount` должен соответствовать именно числу заказов, а не числу позиций.

---

# 13. Аддитивность показателей

Некоторые показатели можно безопасно суммировать при переходе на более высокий уровень.

Например:

```text
Revenue
UnitsSold
```

Для текущей ЛР глобальные значения:

```text
Units = 62
Revenue = 2 279 410.00
```

Если построенный VIEW правильно разбивает продажи на непересекающиеся группы, повторное `SUM` этих показателей должно восстановить общий итог.

---

# 14. Почему `OrdersCount` нельзя бездумно суммировать

Представим один заказ:

```text
Order 1001
├── Laptop
└── Mouse
```

Если товары относятся к разным категориям:

```text
Ноутбуки   OrdersCount = 1
Периферия  OrdersCount = 1
```

Простая сумма:

```text
1 + 1 = 2
```

не означает, что было два заказа.

Один и тот же заказ вошёл в две категории.

Поэтому:

> `OrdersCount` по категориям не является полностью аддитивным показателем.

Для общего числа заказов нужен отдельный расчёт на соответствующем grain.

---

# 15. Средние значения требуют осторожности

Среднее нельзя автоматически суммировать.

Также не всегда корректно делать:

```sql
AVG(AvgOrderValue)
```

по уже агрегированным группам.

Надёжный подход — сохранять базовые компоненты:

```text
Revenue
OrdersCount
```

и рассчитывать:

```text
Revenue / OrdersCount
```

на нужном уровне.

---

# 16. Средняя историческая цена товара

В `vw_ProductPerformance` требуется средняя фактическая цена проданной единицы.

Важно различать:

```text
Products.Price
→ текущая цена каталога
```

и:

```text
FactSales.Price / FactSales.Amount
→ история совершённых продаж
```

Пусть товар продавался:

```text
1 шт. × 100
3 шт. × 80
```

Простое:

```sql
AVG(Price)
```

даст:

```text
90
```

Но реальная средняя цена одной проданной единицы:

```text
(100 + 240) / 4 = 85
```

Поэтому взвешенная историческая цена:

```sql
SUM(Amount) / SUM(Quantity)
```

лучше соответствует смыслу показателя.

---

# 17. Зачем `NULLIF` в делении

При расчёте отношения полезно защищаться от деления на ноль.

Пример:

```sql
SUM(Amount)
/
NULLIF(COUNT(DISTINCT OrderID), 0)
```

`NULLIF(x, 0)` возвращает `NULL`, когда `x = 0`, и предотвращает ошибку деления на ноль.

---

# 18. Почему `ORDER BY` не хранится в VIEW

VIEW задаёт табличный результат, но не гарантирует порядок строк.

Правильная идея:

```sql
SELECT *
FROM mart.SomeView
ORDER BY Revenue DESC;
```

Сортировка относится к конечному `SELECT`.

Обычный VIEW нельзя воспринимать как заранее отсортированный файл.

---

# 19. `CREATE OR ALTER VIEW`

В SQL Server удобно использовать:

```sql
CREATE OR ALTER VIEW mart.vw_Example
AS
SELECT ...
GO
```

Если объекта ещё нет — он создаётся.

Если существует — его определение изменяется.

Это удобно при повторном запуске разработки.

`GO` — разделитель batch, понимаемый клиентскими инструментами SQL Server.

# 21. Системные представления

В ЛР3 системные представления используются как инструмент проверки собственного проекта.

## `sys.views`

Содержит сведения о VIEW текущей базы:

```sql
SELECT
    name,
    object_id
FROM sys.views;
```

## `sys.schemas`

Позволяет определить схему:

```sql
SELECT
    s.name AS SchemaName,
    v.name AS ViewName
FROM sys.views AS v
JOIN sys.schemas AS s
    ON s.schema_id = v.schema_id;
```

## `sys.columns`

Показывает столбцы объекта:

```sql
SELECT
    column_id,
    name
FROM sys.columns
WHERE object_id = OBJECT_ID(N'mart.SomeView');
```

## `sys.types`

Позволяет вывести типы столбцов:

```sql
SELECT
    c.name,
    t.name AS DataType
FROM sys.columns AS c
JOIN sys.types AS t
    ON t.user_type_id = c.user_type_id
WHERE c.object_id = OBJECT_ID(N'mart.SomeView');
```

# 22. `OBJECT_ID`

# 26. Контроль глобальных сумм

Для четырёх обязательных VIEW аддитивные показатели должны восстанавливать общий итог:

```text
Units = 62
Revenue / TotalSpent = 2 279 410.00
```

Если итог меньше:

- потеряны строки;
- неверный `JOIN`;
- лишний `WHERE`;
- часть групп исключена.

Если итог больше:

- строки размножены `JOIN`;
- нарушена кардинальность;
- факт присоединён к неуникальному набору.

# 28. Почему проверяется и количество строк, и сумма

Одна сумма не гарантирует правильный grain.

Например две группы можно ошибочно объединить, но:

```text
SUM(Revenue)
```

останется тем же.

Поэтому итоговая проверка использует одновременно:

```text
row count
+
Units
+
Revenue
+
контрольные лидеры
```

# 29. Типичные ошибки

## `COUNT(*)` вместо числа заказов

Симптом:

```text
OrdersCount
```

похож на число строк факта.

Причина:

```sql
COUNT(*)
```

вместо:

```sql
COUNT(DISTINCT OrderID)
```

## Неверный grain

Если в product-view добавить месяц:

```text
ProductID
ProductName
Month
Revenue
```

то одна строка уже не означает один товар.

Контроль `20 строк` перестанет выполняться.

## Размножение строк `JOIN`

Одна строка факта может превратиться в несколько строк.

Симптом:

```text
Revenue > 2 279 410.00
```

## `AVG(Price)` вместо взвешенной цены

При `Quantity > 1` простое среднее цен строк может давать неверную среднюю стоимость физической единицы.

## Сортировка внутри VIEW

`ORDER BY` не должен использоваться как способ «сохранить» порядок обычного VIEW.


# 32. Как проверить один VIEW

Общий подход:

```sql
SELECT *
FROM mart.SomeView;
```

Затем:

```sql
SELECT COUNT(*)
FROM mart.SomeView;
```

И отдельно:

```sql
SELECT
    SUM(SomeUnits),
    SUM(SomeRevenue)
FROM mart.SomeView;
```

Количество строк помогает проверить grain.

Суммы помогают проверить отсутствие потерь и размножения данных.

# 37. Что важно понять после работы

Главный результат ЛР3 — не четыре конструкции `CREATE VIEW`.

Архитектурная цепочка:

```text
бизнес-вопрос
      ↓
measure + dimension
      ↓
grain
      ↓
аналитический SELECT
      ↓
VIEW
      ↓
предметный Data Mart
```

И отдельно:

```text
один Data Mart
≠
один grain
```

Один предметный аналитический слой может включать несколько VIEW с разным grain, если они обслуживают одну согласованную область задач.

Это и есть основная архитектурная идея третьей практической работы.
